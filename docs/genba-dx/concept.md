# 現場DXツール 構想メモ（仮称: genba-dx）

> 配車表を起点に、当日の現場状況をチャットで確認・承認する「日報レス」DXツールの構想・設計ドキュメント。
> ステータス: アイデア検討中（壁打ちメモ）。確定仕様ではない。

最終更新: 2026-06-25

---

## 1. 背景と課題

日報文化のない会社（建設・運送・設備・清掃・警備など、現場が分散する労働集約型の業種）では、
日々の運用が口頭・電話・紙・個人LINEで回っており、以下が記録に残らない／集計できない。

- 当日、**誰がどの現場に行ったのか**
- **欠員**が出たのか、出たならどう埋めたのか
- **残業**が発生したのか、その承認はどうなったのか
- 現場ごとの稼働実態（後から振り返れない）

「日報を書かせればよい」という話だが、ITが苦手・多忙な現場ほど **入力が定着しない**。
ここが根本のボトルネック。

## 2. ソリューションの考え方

**「書かせる」のではなく「聞いて、答えてもらう」** に発想を変える。

1. 管理者が **配車表（＝当日の人員アサイン）** を作る（既存業務そのまま）
2. 当日、各現場の **代表者のスマホへ確認画面を自動送付**
3. 代表者は **ボタン中心で回答**（来た／欠員あり／残業あり 等）
4. 管理者は **管理画面で確認・承認**
5. 回答が **そのまま記録（＝日報の代替）として蓄積**

配車表という既にある業務を入口にすることで、現場側は「新しく覚えること」がほぼゼロになる。

```
[管理者] 配車表を作成
        │
        ▼
[システム] 当日朝、各現場代表者へ確認画面を配信（Push / LINE / メール）
        │
        ▼
[現場代表者] スマホでボタン回答（人員・欠員・残業 など）
        │
        ▼
[管理者] 管理画面で確認・承認
        │
        ▼
[システム] 記録として蓄積（集計・振り返り・将来は勤怠/給与連携）
```

## 3. ユーザーロール

| ロール | 役割 |
|---|---|
| 管理者（事務／配車担当） | 配車表の作成、確認画面の配信、回答の確認・承認、集計閲覧 |
| 現場代表者 | 当日割り当てられた現場の確認画面に回答 |
| 作業員（将来） | 自身の出欠・残業を個別に回答（MVPでは代表者がまとめて回答） |

## 4. 主要フロー（MVP）

1. **配車表作成** — 管理者が「日付 × 現場 × 配置メンバー」を入力
2. **配信** — 当日（または前日夜）に各現場代表者へ確認リンクを送付
3. **現場回答** — 代表者が確認画面で回答
   - 予定メンバーは揃ったか（欠員の有無、誰が欠けたか）
   - 残業の有無・時間・理由（残業申請）
   - 自由記述メモ（任意）
4. **承認** — 管理者が内容を確認し承認／差し戻し
5. **蓄積** — 承認済み記録を一覧・検索・集計

## 5. 画面一覧（MVP）

**管理画面（PC中心）**
- 配車表エディタ（日付ごとに現場とメンバーを割り当て）
- 当日ダッシュボード（現場ごとの回答状況: 未回答/回答済/承認済）
- 回答詳細・承認画面
- 記録一覧／集計（期間・現場・人ごと）

**現場用画面（スマホ中心 / PWA）**
- 本日の確認画面（割り当てメンバー表示 → ボタン回答）
- 残業申請フォーム
- 回答完了画面

## 6. データモデル案

抽象度を上げて、業種非依存にするのがポイント。「配車」を **assignment（割り当て）** と一般化する。

```
company        会社（テナント）
  └ user       ユーザー（role: admin / leader / worker）
  └ site       現場・拠点（名称・住所など）
  └ shift_day  営業日（日付単位の親）
       └ assignment   その日の「現場 × 担当メンバー」割り当て
              └ report  現場代表者の回答
                   - attendance（出欠・欠員）
                   - overtime（残業の有無/時間/理由）
                   - note（自由記述）
                   - status（draft / submitted / approved / rejected）
```

- マルチテナント前提（`company_id` で必ずスコープ）
- `report.status` で承認フローを表現
- 通知は `notification`（宛先・チャネル・送達状態）として別テーブルに

## 7. 技術スタック案

| 領域 | 採用候補 | 理由 |
|---|---|---|
| フロント / 管理画面 | Next.js（App Router）+ PWA | 現場はインストール不要のWeb、管理はリッチに |
| 認証・DB・API | Supabase（Postgres + Auth + RLS） | 小規模に強く、マルチテナントをRLSで担保しやすい |
| 通知 | Web Push を主軸、**LINE Messaging API / メールにもフォールバック** | 「アプリを開かなくても届く」を担保し普及の壁を下げる |
| ホスティング | Vercel または Cloudflare | 既存資産（Cloudflare）とも親和 |

### 独自アプリ vs LINE の整理
- 自由度・拡張性・他業種展開を考えると **独自Webアプリ（PWA）が本体** であるべき。
- ただし普及の壁（インストール・IT不慣れ）対策として、**通知はLINE/メールにも飛ばせる** 折衷設計にする。

## 8. 汎用化の論点

「配車表」は建設・運送のメンタルモデルだが、本質は **「日次のアサイン → 現場確認 → 承認」**。
これを抽象化すれば以下にも展開できる：

- 清掃・ビルメンテ（誰がどの物件へ）
- 警備（誰がどの現場へ、欠員は致命的）
- 介護・訪問系（訪問先アサインと実施報告）
- イベント・派遣（日々違う現場へ人を配置）

→ 用語を設定で切り替え可能にする（「現場」「物件」「訪問先」など）と汎用プロダクト化しやすい。

## 9. MVPスコープ と ロードマップ

**MVP（まず1日サイクルを通す）**
- 配車表作成（管理画面）
- 当日確認画面の配信（まずはWeb Push or メールリンク）
- 現場代表者のボタン回答（欠員・残業）
- 管理画面での承認・一覧

**フェーズ2**
- 残業集計・期間レポート、CSVエクスポート
- LINE通知連携
- 作業員個別回答

**フェーズ3**
- 勤怠／給与システム連携
- 用語カスタマイズによる多業種対応
- 過去配車表の取り込み（OCR資産の活用余地）

- 認証方法（現場代表者にアカウントを持たせるか、リンク+暗証で軽量にするか）
- リポジトリ名の確定（仮称 genba-dx）
