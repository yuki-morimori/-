# らくらく手配 — 構想メモ

> 配車表を起点に、当日の現場状況をチャットで確認・承認する「日報レス」DXツール。
> プロダクト名: **らくらく手配**（旧仮称 genba-dx）
> ステータス: 構想・設計の壁打ちメモ。確定仕様ではない。
> 関連: 画面ワイヤーフレームは [wireframes.md](./wireframes.md)

最終更新: 2026-06-25

---

## 1. 背景と課題

日報文化のない会社（建設・運送・設備・清掃・警備など、現場が分散する労働集約型の業種）では、
日々の運用が口頭・電話・紙・個人LINEで回っており、以下が記録に残らない／集計できない。

- 当日、**誰がどの現場に行ったのか**
- **欠員**が出たのか、出たならどう埋めたのか
- **残業**が発生したのか、その承認はどうなったのか
- 現場ごとの稼働実態（後から振り返れない）

「日報を書かせればよい」という話だが、ITが苦手・多忙な現場ほど **入力が定着しない**。
ここが根本のボトルネック。

> **当面の最優先は「手配（配車）を楽にする」一点突破**。集計や勤怠/給与連携などの"出口"は将来フェーズ（§15）。

### 出発点：既存のホワイトボード運用とその限界
- 配車担当は Zoom ホワイトボードで、**グリッド（1セル＝1現場）に色付き付箋（人）を置く**形で運用していた。
- 作成者本人は回せたが、**他の人が使いこなせなかった**。理由は「自由すぎて暗黙ルールが共有されない」こと：
  - 置き方のルールが人によってバラバラ／色や赤字の意味が共有されない（凡例がない）
  - 件数が増えると **欠員・重複が目視頼り** で漏れる
  - 検索・集計・履歴が残らない
- 一方で **「複数人で同じ画面を共有して触れる」点は良かった** → この良さは残す（§6.10 リアルタイム共同編集）。
- → **らくらく手配の使命は「俯瞰できるグリッド＋共有の良さは残しつつ、暗黙ルールをシステムが肩代わりして"誰でも使える"ようにする」こと。**

### 現場の前提（重要な制約）
- **全員がスマホを持っているとは限らない／持っていてもリテラシーが低い**。
  → 個別回答に頼らず、**現場代表者が全員分をまとめて回答**する方式を基本とする。
- **現場は電波が悪いことがある**（建設・地下・郊外）。→ オフライン対応が必要（§14）。

## 2. ソリューションの考え方

**「書かせる」のではなく「聞いて、答えてもらう」** に発想を変える。

1. 管理者が **配車表（＝当日の人員・車両アサイン）** を作る（既存業務そのまま）
2. 当日、各現場の **代表者のスマホへ確認画面を自動送付**
3. 代表者は **ボタン中心で回答**（来た／欠員あり／残業あり 等）
4. 管理者は **管理画面で確認・承認**（欠員が出たら**その場で再アサイン**）
5. 回答が **そのまま記録（＝日報の代替）として蓄積**

配車表という既にある業務を入口にすることで、現場側は「新しく覚えること」がほぼゼロになる。

```
[管理者] 配車表を作成（複数人で共同編集可）
        │
        ▼
[システム] 当日朝、各現場代表者へ確認画面を配信（Push / LINE / メール）
        │   └─ 未回答は自動リマインド → さらに無反応ならエスカレーション
        ▼
[現場代表者] スマホでボタン回答（人員・欠員・残業 など / オフラインでも入力可）
        │
        ▼
[管理者] 管理画面で確認・承認（欠員はその場で再アサイン → 変更を再通知）
        │
        ▼
[システム] 記録として蓄積（集計・振り返り・将来は勤怠/給与連携）
```

## 3. ユーザーロール

| ロール | 役割 |
|---|---|
| 管理者（事務／配車担当） | 配車表の作成（共同編集）、確認画面の配信、回答の確認・承認、集計閲覧 |
| 現場代表者 | 当日割り当てられた現場の確認画面に、**現場全員分をまとめて回答** |
| 作業員（将来） | 自身の出欠・残業を個別に回答（当面は代表者が代行） |

## 4. 主要フロー（MVP）

1. **配車表作成** — 管理者が「日付 × 現場 × 配置メンバー × 車両」を入力（1から作成・複数人で共同編集可）
2. **配信** — 当日（または前日夜）に各現場代表者へ確認リンクを送付。**未回答には自動リマインド → 無反応はエスカレーション**（§14）。
3. **現場回答** — 代表者が確認画面で **現場メンバー全員分をまとめて回答**
   - 予定メンバーは揃ったか（欠員の有無、誰が欠けたか）
   - 残業の有無・時間・理由（残業申請）
   - 自由記述メモ（任意）
   - **到着の位置情報（任意）** … 送りたい会社だけON。マストにはしない。
   - ※電波が悪くてもオフラインで入力 → 回復時に自動送信（§14）。
4. **承認・再アサイン** — 管理者が内容を確認し承認／差し戻し。**欠員が出たらダッシュボードからエディタへ飛び、空き人員をドラッグで即補充 → 変更を関係者に再通知**。
5. **蓄積** — 承認済み記録を一覧・検索・集計（**まずは記録として残すことを目的にする**）

## 5. 画面一覧（MVP）

**管理画面（PC / スマホ両対応）**
- 配車表エディタ（日付ごとに現場とメンバー・車両を割り当て・共同編集）→ 詳細は §6
- 当日ダッシュボード（現場ごとの回答状況: 未回答/回答済/承認済）
- 回答詳細・承認画面
- 記録一覧／集計（期間・現場・人ごと）

**現場用画面（スマホ中心 / PWA）**
- 本日の確認画面（割り当てメンバー一覧 → 全員分をまとめてボタン回答）
- 残業申請フォーム
- 回答完了画面

## 6. 配車表（番割表）エディタ UI設計 ★最重要画面

このプロダクトの体験の核。**既存ホワイトボードの「グリッドで俯瞰」「共有で触れる」を活かしつつ、暗黙ルールを構造化**して誰でも使えるようにする。**直感的・便利・「やりたいこと」を予測** を最優先。

### 6.1 基本構成：3フィールド（人員プール / 車両プール / 配車フィールド）

```
┌──────────┬──────────────────────────────────┬──────────┐
│ 人員プール   │  配車フィールド（現場カードのグリッド）      │ 車両プール   │
│(色=タグ)   │  ┌─A現場(3/4)─┐ ┌─B現場(2/2)✓┐      │ 🚚 1号車   │
│ 🟦田中(運) │  │ 田中 佐藤 鈴木│ │ 山本 伊藤    │      │ 🚙 2号車   │
│ 🟩中村(新) │  │ ＋空き1(欠員!)│ │ 🚚1号車     │      │ 🚐 3号車   │
│ 渡辺 …    │  └────────────┘ └────────────┘      │ …        │
└──────────┴──────────────────────────────────┴──────────┘
```

- **人員プール**（左）… 全従業員を自動整列。**色＝タグ**（§6.5）を凡例つきで表示。
- **配車フィールド**（中央）… 既存ホワイトボード同様、**1カード＝1現場のグリッド**。人・車両をここへ置く。
- **車両プール**（右）… 車両を別管理。ここから現場カードへドラッグ。
- 配車表は **1から作成**（既存Excelの取り込みはMVPでは行わない）。

### 6.2 操作（必須要件）
- **長押しドラッグ&ドロップ** … 「長押し→持ち上げ→移動→離してスナップ」。誤操作防止のため長押し起動は必須。人も車両も同じ操作で置ける。**PC・スマホ両方でドラッグ可能**（§6.9）。
- **フィールド内の自動整列** … カード内はグリッドに自動スナップ。空きスロットへ自動で詰める。

### 6.3 現場カードの中身（取引先ごとの項目テンプレ）
- 現場カードに載る項目：**会社名・現場名・集合時間・必要人数・作業内容・持ち物**。
- **取引先ごとに必要項目をチェックボックスでON/OFF**（その取引先の現場は毎回同じ項目だけ表示＝入力が軽く、抜け漏れも防ぐ）。
  - 例）A社は「集合時間・持ち物」必須、B社は「作業内容」必須、など取引先の運用に合わせる。
- 必要項目の設定は取引先マスタに保存し、現場作成時に自動適用。

### 6.4 状況の可視化（目視頼りをやめる）
- プールでは **配置済みの人も薄く残す**（誰を使ったか／誰が余っているかが常に見える）。
- 各カードに **「現在◯/必要◯」カウンタ**。定員到達で✓、不足は **欠員バッジ（赤）**。
- **重複配置**（同一人物・同一車両を複数現場へ）は即アラート。
- **車両×運転可能の連動ガード**：車両を置いたのに、その現場に **「運転可能」タグの人がいない** 場合は警告。
- **アラートパネル**（画面隅にサマリ）：例「運転手不在: 2現場 / 欠員: 3現場 / 資格不足: 1現場」。
  件数が増えても**目視に頼らず**、潰すべき所が一目で分かる（"他人が使えなかった"の核心への回答）。

### 6.5 人員の属性＝タグ（やさしい色分け & 賢い条件マッチングの2段構え）

**ダブルスタンダード**：リテラシーに関わらず使えるよう、同じ「タグ」が2つの使い方を兼ねる。

- **やさしいモード（誰でも）** … タグは **名前＋色** だけ。ホワイトボードの色付箋感覚で、意味づけ不要で塗れる。
  種別の設定をしなくても普通に色分けとして機能する。
- **賢いモード（慣れたら）** … タグに **種別** を設定すると、システムが自動で手伝ってくれる。

| タグの種別 | 例 | システムの動き |
|---|---|---|
| 能力（できること） | 運転可能・玉掛け・フォーク | 現場/車両の「必要条件」と**自動マッチング**して過不足を警告 |
| 区分（状態） | 新人・応援・外注 | 色で識別するだけ（情報表示） |
| 役割 | リーダー/職長 | **現場代表者の自動指名候補**になる |

- タグ（名前・色・アイコン・種別）は **すべてユーザー定義**（後から自由に追加・編集できる＝幅を確保）。
- **1人が複数タグ可**：表示は **枠線色＝代表タグ1つ**、**小アイコンバッジ＝その他タグ**で見やすく。
- **能力フィルタ**：凡例の「🚗運転可能」をタップ → プールが**該当者だけ点灯**（他は薄く）。
  「この現場の運転手、誰が空いてる？」が一瞬で分かる。
- ※初期プリセットタグ（運転可能/新人 等）は用意しつつ、配色・体系は今後さらに煮詰める（§16）。

### 6.6 「やりたいこと」を予測する仕組み（差別化ポイント）
1. **前回の配車を自動再現** … 「いつものメンバー」をワンタップで前日コピー → 変更点だけ動かす。
2. **現場ごとの常連サジェスト** … その現場によく入る人・車両を上位表示／ハイライト。
3. **必要条件に基づくサジェスト** … 運転手不在なら運転可能な空き人員を提案、など。
4. **欠員の即・再アサイン** … 現場から欠員報告が来たら、その現場へ**空いている人をワンタップ/ドラッグで補充**（ダッシュボード→エディタ連携）。
5. **重複・欠員・運転可能者なしの自動警告**（§6.4）。
6. **ドラッグ中に置ける場所をハイライト** … どこに落とせるか迷わせない。

### 6.7 マスタ連動（取引先・現場の自動生成／二重登録の防止）
- マスタは **事前整備を不要**にし、**配車フィールドへの入力で自動的に育てる**。
- 新規カード作成時の挙動：
  1. **会社名（取引先）を入力** → 既存ならサジェスト、無ければ**その場で取引先マスタへ登録**。
  2. **現場名を入力** → 同様に**現場マスタへ登録**し、上記の取引先に**自動で紐づけ**。
  3. 次回以降は**オートコンプリート候補**として表示（§6.6の予測と一体）。
- **二重登録を作らせない（重要要件）**：
  - 入力中は **既存候補のサジェストを最優先で表示**し、まず既存へ寄せる。
  - 登録前に **正規化キーで重複チェック**（前後空白除去・全半角/大文字小文字統一・「(株)/株式会社」等の表記ゆれ吸収）。
  - 一致候補があれば「新規作成」ではなく **既存を選ぶよう促す**。
  - それでも生じた重複は **マスタ統合（マージ）機能**で後から1件に寄せられるようにする（フェーズ2）。

### 6.8 マスタの「ダブルスタンダード」（しっかり vs ズボラ）
- 取引先・現場・車両・人員のマスタは、**作り込み度合いを会社が選べる**。
  - **しっかり使う会社**：項目をきちんと埋めてマスタとして活用（テンプレ・必要条件・点検期限など）。
  - **ズボラな会社**：**名前だけのオブジェクト**として作れれば十分（他項目は任意・後追いでOK）。
- これにより「最初からカッチリ整備しないと使えない」を回避し、**まず動かせる**。

### 6.9 レスポンシブ / スマホ操作（譲れない要件）
- 基本は **3フィールドの横並び**（PC/タブレット）。**会社規模・現場数に応じて幅を自動最適化**。
- **スマホでも"確認"だけでなく"操作"までできる**ことを必須要件とする（閲覧専用にはしない）。
  - dnd-kit の **タッチ対応**で、スマホでも**長押しドラッグで配車**できる。
  - 狭幅では「**1現場ずつフォーカス表示**」「人員/車両プールは**ドロワーで引き出す**」など、
    小さい画面でもドラッグ先を見失わないUIにする。

### 6.10 リアルタイム共同編集（Zoomホワイトボードのような"共有で触れる"）
- 既存ホワイトボードの良さ＝**みんなで同じ盤面を同時に触れる**を再現する。
- **複数人が同時に同じ配車表を編集**でき、**変更は即座に全員へ反映**。
- **プレゼンス表示**：今オンラインで見ている人のアバター、誰がどのカードを触っているかを表示。
- 技術方針（段階的）：
  - **MVP：Supabase Realtime**（DB変更のブロードキャスト＋presence）。
    競合は「楽観ロック＋後勝ち（last-write-wins）」で実用上は十分。
  - **将来：CRDT（Yjs等）** … 同一カードの激しい同時編集まで競合なく扱いたくなったら導入。

### 6.11 技術メモ
- ドラッグ&ドロップは **dnd-kit**（React・タッチ対応・長押し起動・自動整列に強い現状の定番）を想定。

## 7. データモデル案

抽象度を上げて、業種非依存にするのがポイント。「配車」を **assignment（割り当て）** と一般化する。
取引先・現場・車両はマスタ化し、`assignment` から参照する（取引先/現場は配車入力で自動生成・§6.7）。
各マスタは **名前さえあれば作れる**（他項目は任意）＝ §6.8 のダブルスタンダード。

```
company        会社（テナント / 自社）
  ├ login_code   ログイン用の会社ID（発行コード）
  └ tag        タグマスタ（ユーザー定義）
       ├ name / color / icon
       └ kind   capability(能力) / status(区分) / role(役割) / none(色のみ)
  └ user       ユーザー
       ├ employee_code   従業員コード（会社内でユニーク）
       ├ pin_hash        4桁PINのハッシュ（平文保存しない）
       ├ role            admin / leader / worker
       ├ tags[]          付与タグ（複数可）／表示は代表タグ＝枠線色
       └ failed_attempts / locked_until   総当たり対策用
  └ client     取引先マスタ（仕事の発注元 / 行き先の会社）   ← 自動生成
       ├ normalized_name  重複判定用の正規化キー
       ├ field_config     必須項目のON/OFF（現場名/集合時間/必要人数/作業内容/持ち物）
       └ site  現場マスタ（取引先に紐づく個別現場）          ← 自動生成
            ├ normalized_name  重複判定用の正規化キー
            ├ 集合時間 / 必要人数 / 作業内容 / 持ち物（任意・field_configに従う）
            └ requirements[]   必要条件（必要な能力タグ・人数など／任意）
  └ vehicle    車両マスタ（名前のみ必須・他は任意）
       ├ 車種 / 定員・積載 / ナンバー / 点検期限（すべて任意）
       └ requirements[]   必要条件（例: 運転可能 1名／任意）
  └ shift_day  営業日（日付単位の親）
       └ assignment   その日の「現場(site) × メンバー × 車両」割り当て
              ├ members[]   配置メンバー
              ├ vehicles[]  配置車両
              ├ updated_at / updated_by  共同編集の競合解決（後勝ち）
              └ report      現場代表者の回答（現場全員分をまとめて1件）
                   - members[]    メンバーごとの出欠・欠員
                   - overtime     残業の有無/時間/理由
                   - note         自由記述
                   - location?    到着位置（任意）
                   - status       draft / submitted / approved / rejected
  └ audit_log  変更履歴（誰が・いつ・何を：配車変更/承認/残業 など）
```

- マルチテナント前提（`company_id` で必ずスコープ）
- 各マスタは **名前のみ必須**、他項目は任意（ズボラ運用OK・後追い入力可）
- `tag.kind` で「色だけ(none)」か「自動チェック対象(capability等)」かを切替＝ダブルスタンダードの実体
- `requirements[]` と `members[].tags` を照合し、**必要条件の過不足を自動判定**（運転可ガードは一例）
- `client 1 ─ 多 site`（同名現場でも取引先が異なれば別レコード）
- `normalized_name` にユニーク制約を張り、**二重登録をDBレベルでも防ぐ**
- `client.field_config` で現場カードの表示項目を取引先ごとに切替
- `assignment.updated_at/by` で共同編集の後勝ち競合解決（§6.10）。リアルタイム同期は Supabase Realtime
- `report` は現場単位で1件、その中に全メンバーの状況を持つ（回答単位=全員分）
- `audit_log` で労務に関わる変更（残業承認・配車変更）の証跡を残す（§14）
- 通知は `notification`（宛先・チャネル・送達状態・リマインド/エスカレーション管理）として別テーブルに
- ログイン記憶用に `device`（信頼済み端末トークン・有効期限）を別テーブルに

## 8. 技術スタック案

| 領域 | 採用候補 | 理由 |
|---|---|---|
| フロント / 管理画面 | Next.js（App Router）+ PWA | 現場はインストール不要のWeb、管理はリッチに。**オフライン対応もPWAで** |
| ドラッグ&ドロップ | dnd-kit | タッチ・長押し起動・自動整列に強い（§6・スマホ操作も） |
| 認証・DB・API | Supabase（Postgres + Auth + RLS） | 小規模に強く、マルチテナントをRLSで担保しやすい |
| リアルタイム共同編集 | Supabase Realtime（→将来 CRDT/Yjs） | 同時編集とプレゼンス（§6.10） |
| オフライン | PWA（Service Worker）＋送信キュー（IndexedDB） | 電波が悪くても入力 → 回復時に自動送信（§14） |
| 通知 | Web Push を主軸、**LINE Messaging API / メールにもフォールバック** | 「アプリを開かなくても届く」を担保し普及の壁を下げる |
| リマインド（定時実行） | Supabase Scheduled Functions / cron | 未回答の自動再通知・エスカレーション |
| ホスティング | Vercel または Cloudflare | 既存資産（Cloudflare）とも親和 |

### 独自アプリ vs LINE の整理
- 自由度・拡張性・他業種展開を考えると **独自Webアプリ（PWA）が本体** であるべき。
- ただし普及の壁（インストール・IT不慣れ）対策として、**通知はLINE/メールにも飛ばせる** 折衷設計にする。

## 9. 認証・ログイン方式

**現場代表者の使い心地を最優先**にしつつ、役割に応じてセキュリティ強度を変える。

### 現場代表者（leader / worker）
- ログインは **会社ID + 従業員コード + 4桁PIN** の3項目。
  - メール不要・アプリ不要。ATMの暗証番号やタイムカード感覚で迷わない。
- **初回ログイン時だけ**3項目を入力 → **その端末を信頼済みとして記憶**（長期セッション）。
  2日目以降は「開くだけ」。
- 通知（Web Push/LINE/メール）のリンクに **署名付きトークン** を埋め、
  タップ → **今日の回答画面に直行（入力ゼロ）**。
- PINを求めるのは「**新しい端末での初回**」や「**重要操作**」のときだけ。

### 管理者（admin）
- 承認権限を持つため **より強い認証**（メール + パスワード等）を別途用意。
- 現場用の4桁PINとは分離する。

### セキュリティ上の注意（4桁PIN対策）
- 4桁=1万通り、かつ会社ID・従業員コードは秘密情報ではない（実質の防御はPINのみ）。
  - **レート制限 + ロックアウト**（例: 5回失敗で一定時間ロック、管理者へ通知）
  - 従業員コードを **連番にしすぎない**（推測されにくく）
  - ログイン試行の監視
- PINは必ず **ハッシュ化して保存**（平文保存しない）。

## 10. ランニングコストの考え方

コストは **「使うほど増える変動費」** と **「規模に依存しない固定費」** に分けて捉える。
要注意なのは前者、特に **通知チャネル**。料金体系（§15）と表裏。

### 使うほど増える変動費（要注意）
| 項目 | コスト構造 | コメント |
|---|---|---|
| LINE通知（Messaging API） | 無料枠は月200通程度。超過は従量課金 | 「毎日 × 現場数」で通数が積み上がる。例: 30現場×22日=660通/月で無料枠超過 |
| メール通知 | 無料枠（月数千通）超で従量 | LINEより単価は安め |
| SMS通知 | 1通あたり数円〜 | 一番高い。極力使わない |
| クラウドOCR（将来） | 読み取りページ単位の従量 | フェーズ3の話 |

### 規模に依存しにくい固定費
| 項目 | 目安 | コメント |
|---|---|---|
| Supabase | 無料枠あり / Pro 約 $25/月 | DB容量・転送量・ユーザー数・Realtime接続増で有料へ |
| ホスティング | 無料枠あり / Pro 約 $20/月 | 商用なら有料プラン推奨 |
| 独自ドメイン | 年 ¥1,500前後 | ほぼ誤差 |

### 方針（コスト最適化）
- **通知の主軸を「Web Push」にする**（ブラウザ/PWAのプッシュは送信コストほぼ¥0）。
  LINE/メールは「Web Pushが届かない人へのフォールバック」に留める。
- MVP・小規模のうちは各サービスの **無料枠でほぼ ¥0** で回せる。
- 実コストが効いてくるのは「LINE通知を全現場に毎日送る」本格運用時。
  → **「Web Push優先 / LINEはフォールバック」** は技術・コスト両面で有効な設計判断。

## 11. 汎用化の論点

「配車表」は建設・運送のメンタルモデルだが、本質は **「日次のアサイン → 現場確認 → 承認」**。
これを抽象化すれば以下にも展開できる：

- 清掃・ビルメンテ（誰がどの物件へ）
- 警備（誰がどの現場へ、欠員は致命的）
- 介護・訪問系（訪問先アサインと実施報告）
- イベント・派遣（日々違う現場へ人を配置）

→ 用語を設定で切り替え可能にする（「現場」「物件」「訪問先」「取引先」など）と汎用プロダクト化しやすい。

## 12. MVPスコープ と ロードマップ

**MVP（まず1日サイクルを通す ＝「手配を楽にする」一点突破）**
- 配車表エディタ（3フィールド・長押しDnD・自動整列・欠員/重複/運転可能ガード・アラートパネル・1から作成）
- **スマホでもドラッグ操作可**（譲れない要件）
- **リアルタイム共同編集＋プレゼンス**（Supabase Realtime）
- 取引先ごとの項目テンプレ（チェックボックス）
- 人員のタグ（やさしい色分け＋種別つきの賢いタグ）・能力フィルタ・車両プール
- 取引先/現場/車両マスタの自動生成（名前だけでも作れる・二重登録防止）
- 当日確認画面の配信（まずはWeb Push or メールリンク）＋**未回答の自動リマインド/エスカレーション**
- **オフライン入力 → 自動送信**（PWA送信キュー）
- 現場代表者の回答（**全員分まとめて**・欠員・残業・**到着位置は任意**）
- 管理画面での承認・一覧（**まずは記録として蓄積**）＋**欠員の即・再アサイン＋変更の再通知**
- **監査ログ**（残業承認・配車変更の証跡）

**フェーズ2**
- 配車の予測機能（前回再現・常連サジェスト・必要条件サジェスト）
- 定期パターン（曜日テンプレ）・協力会社のゲスト人員
- マスタ統合（マージ）・表記ゆれ整理
- 軽い集計・期間レポート、CSVエクスポート（"出口"の第一歩）
- LINE通知連携
- 作業員個別回答
- CRDT（Yjs）による高度な同時編集

**フェーズ3**
- 勤怠／給与システム連携（本格的な"出口"）
- 用語カスタマイズによる多業種対応
- 過去配車表の取り込み（OCR資産の活用余地）

## 13. これまでに確定した方針

- **プロダクト名：らくらく手配**。狙いは「ホワイトボードの俯瞰感・共有の良さを残しつつ、暗黙ルールを構造化して誰でも使える配車表」。
- **当面の最優先は「手配を楽にする」一点突破**。集計・勤怠/給与などの出口は将来（§15）。
- 本体は **独自Webアプリ（PWA）**、通知は Web Push 優先 + LINE/メールはフォールバック。
- 認証は **現場代表者=会社ID+従業員コード+4桁PIN / 管理者=強めの認証**、初回以降は端末記憶 + 通知リンク直行。
- 配車表エディタは **3フィールド**、**長押しドラッグ&ドロップ + 自動整列** を必須。**スマホでも操作可（閲覧専用にしない）**。
- **リアルタイム共同編集＋プレゼンス**（MVPは Supabase Realtime、将来 CRDT）。
- 現場カード項目は **取引先ごとにチェックボックスでON/OFF**。
- 人員の属性は **ユーザー定義タグ**（色だけ／種別つきの賢い条件マッチングのダブルスタンダード）。能力フィルタあり。
- 車両は別プール。**必要条件を自動チェック**し**アラートパネル**で漏れを一望。
- **マスタは名前だけでも作れる**（しっかり／ズボラ両対応）。配車入力で自動生成・**二重登録を作らせない**。
- **回答単位は現場全員分まとめて（代表者が代行）**。前提：全員がスマホを持たない/リテラシー低めのため個別回答に頼らない。
- **配車表は1から作成**（Excel取り込みはMVP対象外）。
- **未回答は自動リマインド→エスカレーション**。**欠員は即・再アサイン＋変更を再通知**。
- **オフライン入力対応**、**到着位置は任意**、**監査ログを持つ**。
- **承認後データはまずは記録のみ**（勤怠/給与連携は将来）。
- **料金は低価格サブスクを基本線**（買い切りはセルフホスト時のみ。詳細は §15）。

## 14. 懸念への対応方針（MVPで織り込む）

現場で"本当に使える"ために、以下を初期から設計に含める。

| 懸念 | 対応方針 |
|---|---|
| 現場の電波が悪い | **PWAでオフライン入力 → 電波回復時に自動送信**（IndexedDBに送信キュー）。送信状態を画面表示。 |
| リマインドしても見ない人 | リマインドの先に **エスカレーション**：一定時間未回答で管理者へプッシュ／代表者へワンタップ発信できる連絡先表示。 |
| 配信後に配車が変わる | 変更時に **「配置が変わりました」を関係者へ再通知**。版を持って古い情報で動くのを防ぐ。 |
| 労務トラブル（言った言わない） | **監査ログ**：残業承認・配車変更を「誰が・いつ・何を」で記録。 |
| 代理回答の精度（残業） | MVPは代表者代行で進めるが、将来 **残業だけは本人確認/異議申し立て** の余地を残す設計に。 |

## 15. マネタイズ方針（検討中）

- このアプリは **サーバ費用が毎月かかり続ける** タイプ。
  → **純粋な買い切りは構造的に赤字リスク**（収入1回・コスト毎月）。
- **基本線：会社単位の低価格定額サブスク**（毎月のコストと収入が釣り合い、小規模会社にも導入しやすい）。
- **例外：買い切りは「顧客が自分のサーバに置く（セルフホスト）」場合のみ成立**（毎月コストが顧客持ち）。
- 折衷案：本体は安価な買い切り＋通知など従量が増える部分だけ実費、も検討余地あり。
- 具体的な価格帯・課金単位（人数 or 現場数）は今後詰める。
