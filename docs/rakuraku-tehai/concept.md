# らくらく手配 — 構想メモ

> 配車表を起点に、当日の現場状況をチャットで確認・承認する「日報レス」DXツール。
> プロダクト名: **らくらく手配**（旧仮称 genba-dx）
> ステータス: 構想・設計の壁打ちメモ。確定仕様ではない。

最終更新: 2026-06-25

---

## 1. 背景と課題

日報文化のない会社（建設・運送・設備・清掃・警備など、現場が分散する労働集約型の業種）では、
日々の運用が口頭・電話・紙・個人LINEで回っており、以下が記録に残らない／集計できない。

- 当日、**誰がどの現場に行ったのか**
- **欠員**が出たのか、出たならどう埋めたのか
- **残業**が発生したのか、その承認はどうなったのか
- 現場ごとの稼働実態（後から振り返れない）

「日報を書かせればよい」という話だが、ITが苦手・多忙な現場ほど **入力が定着しない**。
ここが根本のボトルネック。

### 出発点：既存のホワイトボード運用とその限界
- 配車担当は Zoom ホワイトボードで、**グリッド（1セル＝1現場）に色付き付箋（人）を置く**形で運用していた。
- 作成者本人は回せたが、**他の人が使いこなせなかった**。理由は「自由すぎて暗黙ルールが共有されない」こと：
  - 置き方のルールが人によってバラバラ／色や赤字の意味が共有されない（凡例がない）
  - 件数が増えると **欠員・重複が目視頼り** で漏れる
  - 検索・集計・履歴が残らない
- → **らくらく手配の使命は「俯瞰できるグリッドの良さは残しつつ、暗黙ルールをシステムが肩代わりして"誰でも使える"ようにする」こと。**

## 2. ソリューションの考え方

**「書かせる」のではなく「聞いて、答えてもらう」** に発想を変える。

1. 管理者が **配車表（＝当日の人員・車両アサイン）** を作る（既存業務そのまま）
2. 当日、各現場の **代表者のスマホへ確認画面を自動送付**
3. 代表者は **ボタン中心で回答**（来た／欠員あり／残業あり 等）
4. 管理者は **管理画面で確認・承認**
5. 回答が **そのまま記録（＝日報の代替）として蓄積**

配車表という既にある業務を入口にすることで、現場側は「新しく覚えること」がほぼゼロになる。

```
[管理者] 配車表を作成
        │
        ▼
[システム] 当日朝、各現場代表者へ確認画面を配信（Push / LINE / メール）
        │
        ▼
[現場代表者] スマホでボタン回答（人員・欠員・残業 など）
        │
        ▼
[管理者] 管理画面で確認・承認
        │
        ▼
[システム] 記録として蓄積（集計・振り返り・将来は勤怠/給与連携）
```

## 3. ユーザーロール

| ロール | 役割 |
|---|---|
| 管理者（事務／配車担当） | 配車表の作成、確認画面の配信、回答の確認・承認、集計閲覧 |
| 現場代表者 | 当日割り当てられた現場の確認画面に、**現場全員分をまとめて回答** |
| 作業員（将来） | 自身の出欠・残業を個別に回答（当面は代表者が代行） |

## 4. 主要フロー（MVP）

1. **配車表作成** — 管理者が「日付 × 現場 × 配置メンバー × 車両」を入力（1から作成）
2. **配信** — 当日（または前日夜）に各現場代表者へ確認リンクを送付
3. **現場回答** — 代表者が確認画面で **現場メンバー全員分をまとめて回答**
   - 予定メンバーは揃ったか（欠員の有無、誰が欠けたか）
   - 残業の有無・時間・理由（残業申請）
   - 自由記述メモ（任意）
4. **承認** — 管理者が内容を確認し承認／差し戻し
5. **蓄積** — 承認済み記録を一覧・検索・集計（**まずは記録として残すことを目的にする**）

## 5. 画面一覧（MVP）

**管理画面（PC中心）**
- 配車表エディタ（日付ごとに現場とメンバー・車両を割り当て）→ 詳細は §6
- 当日ダッシュボード（現場ごとの回答状況: 未回答/回答済/承認済）
- 回答詳細・承認画面
- 記録一覧／集計（期間・現場・人ごと）

**現場用画面（スマホ中心 / PWA）**
- 本日の確認画面（割り当てメンバー一覧 → 全員分をまとめてボタン回答）
- 残業申請フォーム
- 回答完了画面

## 6. 配車表（番割表）エディタ UI設計 ★最重要画面

このプロダクトの体験の核。**既存ホワイトボードの「グリッドで俯瞰」を活かしつつ、暗黙ルールを構造化**して誰でも使えるようにする。**直感的・便利・「やりたいこと」を予測** を最優先。

### 6.1 基本構成：3フィールド（人員プール / 車両プール / 配車フィールド）

```
┌──────────┬──────────────────────────────────┬──────────┐
│ 人員プール   │  配車フィールド（現場カードのグリッド）      │ 車両プール   │
│(色=属性)   │  ┌─A現場(3/4)─┐ ┌─B現場(2/2)✓┐      │ 🚚 1号車   │
│ 🟦田中(運) │  │ 田中 佐藤 鈴木│ │ 山本 伊藤    │      │ 🚙 2号車   │
│ 🟩中村(新) │  │ ＋空き1(欠員!)│ │ 🚚1号車     │      │ 🚐 3号車   │
│ 渡辺 …    │  └────────────┘ └────────────┘      │ …        │
└──────────┴──────────────────────────────────┴──────────┘
```

- **人員プール**（左）… 全従業員を自動整列。**色＝属性**（運転可能/新人など）を凡例つきで表示。
- **配車フィールド**（中央）… 既存ホワイトボード同様、**1カード＝1現場のグリッド**。人・車両をここへ置く。
- **車両プール**（右）… 車両を別管理。ここから現場カードへドラッグ。
- 配車表は **1から作成**（既存Excelの取り込みはMVPでは行わない）。

### 6.2 操作（必須要件）
- **長押しドラッグ&ドロップ** … 「長押し→持ち上げ→移動→離してスナップ」。誤操作防止のため長押し起動は必須。人も車両も同じ操作で置ける。
- **フィールド内の自動整列** … カード内はグリッドに自動スナップ。空きスロットへ自動で詰める。

### 6.3 現場カードの中身（取引先ごとの項目テンプレ）
- 現場カードに載る項目：**会社名・現場名・集合時間・必要人数・作業内容・持ち物**。
- **取引先ごとに必要項目をチェックボックスでON/OFF**（その取引先の現場は毎回同じ項目だけ表示＝入力が軽く、抜け漏れも防ぐ）。
  - 例）A社は「集合時間・持ち物」必須、B社は「作業内容」必須、など取引先の運用に合わせる。
- 必要項目の設定は取引先マスタに保存し、現場作成時に自動適用。

### 6.4 状況の可視化（目視頼りをやめる）
- プールでは **配置済みの人も薄く残す**（誰を使ったか／誰が余っているかが常に見える）。
- 各カードに **「現在◯/必要◯」カウンタ**。定員到達で✓、不足は **欠員バッジ（赤）**。
- **重複配置**（同一人物・同一車両を複数現場へ）は即アラート。
- **車両×運転可能の連動ガード**：車両を置いたのに、その現場に **「運転可能」属性の人がいない** 場合は警告。
- （将来）新人だけの現場など、属性の偏りも注意表示できるようにする。

### 6.5 人員の属性（色分け）
- 人に **属性タグ**を付け、プール/カード上で **色**で識別（凡例つき）。
- 初期想定：**運転可能 / 新人**。属性は **追加・編集できる拡張式**にする。
- ※配色・属性の体系は今後さらに煮詰める（§14）。

### 6.6 「やりたいこと」を予測する仕組み（差別化ポイント）
1. **前回の配車を自動再現** … 「いつものメンバー」をワンタップで前日コピー → 変更点だけ動かす。
2. **現場ごとの常連サジェスト** … その現場によく入る人・車両を上位表示／ハイライト。
3. **重複・欠員・運転可能者なしの自動警告**（§6.4）。
4. **ドラッグ中に置ける場所をハイライト** … どこに落とせるか迷わせない。

### 6.7 マスタ連動（取引先・現場の自動生成／二重登録の防止）
- マスタは **事前整備を不要**にし、**配車フィールドへの入力で自動的に育てる**。
- 新規カード作成時の挙動：
  1. **会社名（取引先）を入力** → 既存ならサジェスト、無ければ**その場で取引先マスタへ登録**。
  2. **現場名を入力** → 同様に**現場マスタへ登録**し、上記の取引先に**自動で紐づけ**。
  3. 次回以降は**オートコンプリート候補**として表示（§6.6の予測と一体）。
- **二重登録を作らせない（重要要件）**：
  - 入力中は **既存候補のサジェストを最優先で表示**し、まず既存へ寄せる。
  - 登録前に **正規化キーで重複チェック**（前後空白除去・全半角/大文字小文字統一・「(株)/株式会社」等の表記ゆれ吸収）。
  - 一致候補があれば「新規作成」ではなく **既存を選ぶよう促す**。
  - それでも生じた重複は **マスタ統合（マージ）機能**で後から1件に寄せられるようにする（フェーズ2）。

### 6.8 レスポンシブ / 画面幅
- 基本は **3フィールドの横並び**（PC/タブレット）。
- **会社規模・現場数に応じて最適な幅に自動調整**。
- **スマホでも確認できる**こと必須。狭い画面ではプール（人員/車両）と配車フィールドを
  タブ切替/スタックに畳み、**閲覧を主**としつつ可能な範囲で操作も担保。

### 6.9 技術メモ
- ドラッグ&ドロップは **dnd-kit**（React・タッチ対応・長押し起動・自動整列に強い現状の定番）を想定。

## 7. データモデル案

抽象度を上げて、業種非依存にするのがポイント。「配車」を **assignment（割り当て）** と一般化する。
取引先・現場・車両はマスタ化し、`assignment` から参照する（取引先/現場は配車入力で自動生成・§6.7）。

```
company        会社（テナント / 自社）
  ├ login_code   ログイン用の会社ID（発行コード）
  └ user       ユーザー
       ├ employee_code   従業員コード（会社内でユニーク）
       ├ pin_hash        4桁PINのハッシュ（平文保存しない）
       ├ role            admin / leader / worker
       ├ attributes[]    属性タグ（運転可能 / 新人 …・色つき・拡張可）
       └ failed_attempts / locked_until   総当たり対策用
  └ client     取引先マスタ（仕事の発注元 / 行き先の会社）   ← 自動生成
       ├ normalized_name  重複判定用の正規化キー
       ├ field_config     必須項目のON/OFF（現場名/集合時間/必要人数/作業内容/持ち物）
       └ site  現場マスタ（取引先に紐づく個別現場）          ← 自動生成
            ├ normalized_name  重複判定用の正規化キー
            └ 集合時間 / 必要人数 / 作業内容 / 持ち物（field_configに従う）
  └ vehicle    車両マスタ（車種・定員/積載・ナンバー など）
  └ shift_day  営業日（日付単位の親）
       └ assignment   その日の「現場(site) × メンバー × 車両」割り当て
              ├ members[]   配置メンバー
              ├ vehicles[]  配置車両
              └ report      現場代表者の回答（現場全員分をまとめて1件）
                   - members[]    メンバーごとの出欠・欠員
                   - overtime     残業の有無/時間/理由
                   - note         自由記述
                   - status       draft / submitted / approved / rejected
```

- マルチテナント前提（`company_id` で必ずスコープ）
- `client 1 ─ 多 site`（同名現場でも取引先が異なれば別レコード）
- `normalized_name` にユニーク制約を張り、**二重登録をDBレベルでも防ぐ**
- `client.field_config` で現場カードの表示項目を取引先ごとに切替
- `assignment` は人(members)と車両(vehicles)の両方を保持。**車両ありなら運転可能者の有無を検証**
- `report` は現場単位で1件、その中に全メンバーの状況を持つ（回答単位=全員分）
- 通知は `notification`（宛先・チャネル・送達状態）として別テーブルに
- ログイン記憶用に `device`（信頼済み端末トークン・有効期限）を別テーブルに

## 8. 技術スタック案

| 領域 | 採用候補 | 理由 |
|---|---|---|
| フロント / 管理画面 | Next.js（App Router）+ PWA | 現場はインストール不要のWeb、管理はリッチに |
| ドラッグ&ドロップ | dnd-kit | タッチ・長押し起動・自動整列に強い（§6） |
| 認証・DB・API | Supabase（Postgres + Auth + RLS） | 小規模に強く、マルチテナントをRLSで担保しやすい |
| 通知 | Web Push を主軸、**LINE Messaging API / メールにもフォールバック** | 「アプリを開かなくても届く」を担保し普及の壁を下げる |
| ホスティング | Vercel または Cloudflare | 既存資産（Cloudflare）とも親和 |

### 独自アプリ vs LINE の整理
- 自由度・拡張性・他業種展開を考えると **独自Webアプリ（PWA）が本体** であるべき。
- ただし普及の壁（インストール・IT不慣れ）対策として、**通知はLINE/メールにも飛ばせる** 折衷設計にする。

## 9. 認証・ログイン方式

**現場代表者の使い心地を最優先**にしつつ、役割に応じてセキュリティ強度を変える。

### 現場代表者（leader / worker）
- ログインは **会社ID + 従業員コード + 4桁PIN** の3項目。
  - メール不要・アプリ不要。ATMの暗証番号やタイムカード感覚で迷わない。
- **初回ログイン時だけ**3項目を入力 → **その端末を信頼済みとして記憶**（長期セッション）。
  2日目以降は「開くだけ」。
- 通知（Web Push/LINE/メール）のリンクに **署名付きトークン** を埋め、
  タップ → **今日の回答画面に直行（入力ゼロ）**。
- PINを求めるのは「**新しい端末での初回**」や「**重要操作**」のときだけ。

### 管理者（admin）
- 承認権限を持つため **より強い認証**（メール + パスワード等）を別途用意。
- 現場用の4桁PINとは分離する。

### セキュリティ上の注意（4桁PIN対策）
- 4桁=1万通り、かつ会社ID・従業員コードは秘密情報ではない（実質の防御はPINのみ）。
  - **レート制限 + ロックアウト**（例: 5回失敗で一定時間ロック、管理者へ通知）
  - 従業員コードを **連番にしすぎない**（推測されにくく）
  - ログイン試行の監視
- PINは必ず **ハッシュ化して保存**（平文保存しない）。

## 10. ランニングコストの考え方

コストは **「使うほど増える変動費」** と **「規模に依存しない固定費」** に分けて捉える。
要注意なのは前者、特に **通知チャネル**。

### 使うほど増える変動費（要注意）
| 項目 | コスト構造 | コメント |
|---|---|---|
| LINE通知（Messaging API） | 無料枠は月200通程度。超過は従量課金 | 「毎日 × 現場数」で通数が積み上がる。例: 30現場×22日=660通/月で無料枠超過 |
| メール通知 | 無料枠（月数千通）超で従量 | LINEより単価は安め |
| SMS通知 | 1通あたり数円〜 | 一番高い。極力使わない |
| クラウドOCR（将来） | 読み取りページ単位の従量 | フェーズ3の話 |

### 規模に依存しにくい固定費
| 項目 | 目安 | コメント |
|---|---|---|
| Supabase | 無料枠あり / Pro 約 $25/月 | DB容量・転送量・ユーザー数増で有料へ |
| ホスティング | 無料枠あり / Pro 約 $20/月 | 商用なら有料プラン推奨 |
| 独自ドメイン | 年 ¥1,500前後 | ほぼ誤差 |

### 方針（コスト最適化）
- **通知の主軸を「Web Push」にする**（ブラウザ/PWAのプッシュは送信コストほぼ¥0）。
  LINE/メールは「Web Pushが届かない人へのフォールバック」に留める。
- MVP・小規模のうちは各サービスの **無料枠でほぼ ¥0** で回せる。
- 実コストが効いてくるのは「LINE通知を全現場に毎日送る」本格運用時。
  → **「Web Push優先 / LINEはフォールバック」** は技術・コスト両面で有効な設計判断。

## 11. 汎用化の論点

「配車表」は建設・運送のメンタルモデルだが、本質は **「日次のアサイン → 現場確認 → 承認」**。
これを抽象化すれば以下にも展開できる：

- 清掃・ビルメンテ（誰がどの物件へ）
- 警備（誰がどの現場へ、欠員は致命的）
- 介護・訪問系（訪問先アサインと実施報告）
- イベント・派遣（日々違う現場へ人を配置）

→ 用語を設定で切り替え可能にする（「現場」「物件」「訪問先」「取引先」など）と汎用プロダクト化しやすい。

## 13. これまでに確定した方針

- **プロダクト名：らくらく手配**。狙いは「ホワイトボードの俯瞰感を残しつつ、暗黙ルールを構造化して誰でも使える配車表」。
- 本体は **独自Webアプリ（PWA）**、通知は Web Push 優先 + LINE/メールはフォールバック。
- 認証は **現場代表者=会社ID+従業員コード+4桁PIN / 管理者=強めの認証**、
  初回以降は端末記憶 + 通知リンク直行で入力ゼロを目指す。
- 配車表エディタは **3フィールド（人員プール / 車両プール / 配車フィールド＝現場カードのグリッド）**、
  **長押しドラッグ&ドロップ + フィールド内自動整列** を必須要件とする。
- 現場カード項目（会社名/現場名/集合時間/必要人数/作業内容/持ち物）は **取引先ごとにチェックボックスでON/OFF**。
- 人員は **属性タグ（運転可能/新人…拡張可・色つき）** を持ち、**車両×運転可能者なしを自動警告**。
- プールは **配置済みも薄く残す**。**欠員・重複は自動検知**（目視頼りをやめる）。
- レイアウトは **横並びを基本**に、**規模・現場数で幅を自動最適化**、**スマホでも確認可能**。
- マスタ（**取引先・現場**）は **配車フィールド入力で自動生成・連動**、**二重登録を作らせない**（サジェスト優先＋正規化キー、将来マージ）。
- **回答単位は「現場全員分をまとめて」**（現場代表者が代行）。
- **配車表は1から作成**（Excel取り込みはMVP対象外）。
- **承認後データはまずは記録のみ**（勤怠/給与連携は将来フェーズ）。
